## Lab 0 — Get your seat

1. Open the portal — **the URL is in your welcome email** (and on your table card at in-person events).
2. Log in with the username and password on your table card (`lab01`…`labNN`).
3. **Your folder today: Core lab.** Sign in once. The portal shows one **folder per lab track**
   running today; your welcome email says which folder is which. For this guide open the folder
   named **Core lab**. On a single-lab day there are no folders — the same two tiles sit at the
   portal root as **Your Lab Server (labNN)** and **Your Lab Server desktop (labNN)**. Inside your
   folder you get **two tiles** — both are your own seat:
   - **Core lab (labNN)** — a **terminal** in the browser tab. The lab happens here.
   - **Core lab desktop (labNN)** — a **desktop** on the *same* server (Firefox, a File
     Manager and a Terminal launcher; it's already logged in, no password to type). Today it's
     for reading the staged SBOMs in Firefox's JSON viewer (Lab 1) and talking to your LLM
     endpoint in a real browser (Lab 4).

   Other folders are **other servers**: files and images do not carry across. Everywhere below,
   **your desktop tile** means **Core lab desktop (labNN)** — or **Your Lab Server desktop (labNN)**
   on a single-lab day.

   **Keep both open.** A tile normally opens in the same browser tab — **Ctrl-click** (or
   middle-click) a tile to open it in a **new browser tab**, so the terminal and the desktop sit
   side by side. Firefox on the desktop reaches anything listening on your seat
   (`http://localhost:<port>`), and the File Manager reaches every file in your home folder.
   Every desktop step below names a launcher *and* the URL or path to type into Firefox — if the
   launcher isn't on your desktop, type it; same result.
4. Clipboard: press **Ctrl+Alt+Shift** to open the side menu, paste into its clipboard box, close
   the menu, then paste normally.

Sanity check:


You should see `pytorch/pytorch`, `cgr.dev/chainguard/pytorch`, and `cgr.dev/<org>/ollama` already

## Lab 1 — Weigh the images

Upstream PyTorch versus Chainguard's — both pre-staged at image-build time. Weigh them:

```bash
docker images | grep -E 'pytorch|REPOSITORY'
```

> [!NOTE]
> No `docker pull` here on purpose: `:latest` moves nightly, and a live pull would re-download
> gigabytes over venue wifi AND re-tag your validated image to an untested build. What's staged
> is what the lab was proven on.


Illustrative sizes: upstream ~**7.42 GB**, Chainguard ~**2.11 GB**. Now count what's inside —
every package is attack surface and patch burden. Your seat carries each image's **SBOM**,
generated by syft when the seat image was built (`~/labs/artifacts/`) — because an image this
big takes ~15 minutes just to *inventory*, that work was done for you overnight:

```bash
ls ~/labs/artifacts/
jq '.packages | length' ~/labs/artifacts/pytorch-upstream-sbom.spdx.json
jq '.packages | length' ~/labs/artifacts/pytorch-chainguard-sbom.spdx.json
```

Browse what an SBOM actually holds — names, versions, licenses, for every single package:

```bash
syft convert ~/labs/artifacts/pytorch-upstream-sbom.spdx.json -o table | less
```

Illustrative counts: ~**384** packages upstream, ~**62** in the Chainguard image. Record your
numbers in the scorecard below.

> [!TIP]
> **On your desktop** (**Core lab desktop (labNN)** — or **Your Lab Server desktop (labNN)** on a
> single-lab day): double-click **SBOMs** (opens `~/labs/artifacts` in the File Manager)
> and open `pytorch-upstream-sbom.spdx.json` — or type
> `file:///home/labuser/labs/artifacts/pytorch-upstream-sbom.spdx.json` into Firefox. In the
> JSON viewer expand `packages` and use the **Filter JSON** box: type `conda` or `cuda` — that's
> the freight. Open `pytorch-chainguard-sbom.spdx.json` the same way and filter again: a much
> shorter list, same torch.

> [!NOTE]
> ⏱ **Want to generate the inventory yourself?** You can — `syft -v pytorch/pytorch:latest`
> — but expect **10–15 minutes** while it unpacks all ~7 GB. You have been warned. (The
> Chainguard image takes ~5 — small is fast in every dimension.) The staged SBOMs are exactly
> what that command produces, minted at seat-build time.

## Lab 2 — Scan them

This is a **live scan with today's vulnerability feed** — you run grype yourself, right now.
The trick: scan the *SBOM*, not the image. The inventory hasn't changed since it was staged;
the CVE knowledge has. Matching one against the other takes seconds, not minutes:

```bash
grype sbom:~/labs/artifacts/pytorch-upstream-sbom.spdx.json
grype sbom:~/labs/artifacts/pytorch-chainguard-sbom.spdx.json
```

Illustrative: **528** known CVEs upstream, **0** in the Chainguard image. Capture your live counts
— these are the numbers you'll quote later.

> [!TIP]
> You just ran the real enterprise workflow: **scan the artifact inventory, not the artifact**.
> The SBOM is generated once per build; every scanner, auditor, and dashboard works from it.
> That's why SBOMs matter — they turn a 15-minute unpack into a 10-second lookup, forever.

Second opinion with a different scanner, criticals only (this one does scan the image — it's
the direct-scan experience if you want it; expect a few minutes):

```bash
trivy image --severity CRITICAL pytorch/pytorch:latest
```

Different scanner, same story — this isn't a grype quirk.

## Lab 3 — Train and infer on the hardened image

A real (small) PyTorch job: train an octopus/whale/penguin classifier, on CPU, inside the
Chainguard image. The wrapper scripts save you a three-line `docker run`:

```bash
cd ~/labs/octopus
cat train.sh
./train.sh
```

Training takes a couple of minutes on this box. When it finishes, a
`octopus_whale_penguin_model.pt` file appears. Now run inference against a picture:

```bash
./infer.sh octopus.jpg
```

Expected output ends with the classifier's verdict: `octopus`. Zero-CVE images aren't demo-ware —
you just trained and served a model on one.

> [!TIP]
> **On your desktop (optional):** double-click **Octopus demo** — or **File Manager** → `labs` → `octopus` —
> `octopus_whale_penguin_model.pt` is the model you just trained; double-click `octopus.jpg` to
> see what it classified.

## Lab 4 — Serve an LLM

gemma3:1b via Ollama from your org's Chainguard catalog, weights pre-staged, CPU-only:

```bash
docker run -d --name llm -p 11434:11434 -v ~/labs/models:/home/nonroot/.ollama cgr.dev/$ORG/ollama:latest
```

(`$ORG` is already set in your shell.) Give it a few seconds, then:

```bash
curl -s localhost:11434/api/generate -d '{"model":"gemma3:1b","prompt":"Why is the sky blue?","stream":false}' | jq -r .response
```

> [!TIP]
> **On your desktop:** double-click **Ollama** — or open **Firefox** and type `http://localhost:11434` — it answers
> `Ollama is running`. Then `http://localhost:11434/api/tags`: the JSON viewer lists `gemma3:1b` —
> the pre-staged weights your endpoint is serving.

A real LLM answer, from a hardened image, on a 2-vCPU box. One more thing worth noticing:

```bash
docker inspect llm --format '{{.Config.User}}'
```

`65532` — the model server runs as a nonroot user out of the box. No root LLM.

## Lab 5 — Prove where it came from

Anyone can claim an image is clean. Chainguard images ship with verifiable provenance:

```bash
cosign verify --certificate-oidc-issuer=https://token.actions.githubusercontent.com --certificate-identity=https://github.com/chainguard-images/images/.github/workflows/release.yaml@refs/heads/main cgr.dev/chainguard/pytorch | jq
```

Exit code 0 and a signature payload: this exact image was built by that exact GitHub Actions
workflow. Now generate the SBOM you'd hand an auditor:

```bash
syft cgr.dev/chainguard/pytorch:latest -o spdx-json > pytorch-sbom.json
jq '.packages | length' pytorch-sbom.json
```

That's a machine-readable inventory of everything in the image — the artifact behind every
"do you have an SBOM?" compliance question.

> [!TIP]
> **On your desktop:** `pytorch-sbom.json` landed in the folder you ran syft from (`pwd` —
> `~/labs/octopus` if you came straight from Lab 3). **File Manager** → that folder → open it, or
> type `file:///home/labuser/labs/octopus/pytorch-sbom.json` into Firefox — the same 62-package
> inventory, in a form an assessor can actually read.
